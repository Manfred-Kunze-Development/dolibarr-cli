## Project Overview

A CLI that surfaces the **complete Dolibarr ERP/CRM REST API** to end users — not a curated subset. The reference instance exposes 440 operations across 38 modules, though the real surface varies per instance (see [The API Surface Is Instance-Dependent](#the-api-surface-is-instance-dependent)).

**This repository is currently empty.** Everything below is either a fact verified against the reference projects, the Dolibarr spec, or the Dolibarr PHP source — or the agreed target architecture. Nothing here has been implemented yet.

### Version Support Policy

**Support exactly three Dolibarr majors at a time: previous, current, next.** Never more.

As of 2026-07-22 that is 22 (previous), 23 (current), 24/`develop` (next). When 24 ships stable
it becomes current, 23 becomes previous, 22 is **dropped**, and `develop` becomes the new next.

This is a hard scope boundary, not a default. It follows directly from the API surface being
instance-dependent — every additional supported major multiplies the surface that has to be
verified. Consequences to honour:

- The CI matrix is these three, and only these three.
- `compose.yml` profiles track them; rolling the window means changing image tags there.
- `required-fields.json` is re-extracted per supported major (`npm run extract:fields`).
- Bug reports against an unsupported major get an upgrade recommendation, not a compatibility
  shim. Do not add version-conditional code for majors outside the window.

Do not widen this window without the user's explicit say-so.

## Technology Stack

Mirror `../backbone/cli`'s stack, with one deliberate divergence:

- Node >= 18, **ESM** (`"type": "module"`), TypeScript `module: Node16` → **all relative imports need the `.js` extension**
- `commander` (command tree), `conf` (config store), `chalk` + `cli-table3` + `ora` (output)
- `tsc` → `dist/`, `bin` entries `dolibarr` and `doli` point at `dist/index.js`
- Tests: `vitest` (as in `../dolibarr-mcp`, which uses unit + contract test split)

**No `openapi-fetch` and no generated types in v1.** The command tree is derived from the live
instance spec at runtime, so every command goes through a generic `request()` and a typed client
would have zero call sites. `openapi-fetch` + the `swagger2openapi -p → openapi-typescript` build
step arrive with the first hand-crafted module. See the design spec for the reasoning.

## The Central Constraint: Dolibarr's Spec Is a Route Catalog, Not a Contract

This is the one thing that makes this repo different from `backbone/cli`, and it drives most design decisions.

**Dolibarr publishes Swagger 2.0, and `openapi-typescript` rejects it outright:**

```
Error: Unsupported Swagger version: 2.x. Use OpenAPI 3.x instead.
```

So the generation pipeline needs a conversion step that `backbone/cli` does not have. Verified working:

```bash
swagger2openapi -p swagger.json -o openapi/openapi.json   # -p (patch) is REQUIRED
openapi-typescript openapi/openapi.json -o src/generated/openapi.d.ts
```

`-p` is not optional — without it the conversion aborts on `path parameters must be required:true` at `POST /proposals/{id}/contact/{contactid}/{type}/{source}`. Dolibarr's spec is generated by Restler and has several such defects.

**More importantly, the generated types describe only the route surface.** What is trustworthy and what is not:

| Generated from spec | Trustworthy? | Notes |
|---|---|---|
| Paths, methods, `operationId`, tags | ✅ Yes | 285 paths, 440 operations, 38 tags |
| Path + query parameters | ✅ Yes | Real names, types, and genuinely useful descriptions |
| **Response bodies** | ❌ **No** | Declared as `Obj` (107×), `string`, `string[]`, or `int64`. e.g. `listThirdparties` is typed `string[]` but returns thirdparty objects. |
| **Entity CRUD request bodies** | ❌ **No** | 101 of 148 definitions are the placeholder `{ request_data: string[] }` — including every `create*`/`update*` for thirdparties, invoices, products, orders … |
| **Action request bodies** | ✅ Yes | 46 models are real: `invoicesAddPaymentModel`, `bankaccountsTransferModel`, `createStockmovementsModel`, `tasksAddTimeSpentModel`, `productsAddPurchasePriceModel`, the `*ValidateModel`/`*CloseModel` family, etc. |

**Consequences:**

1. Use the generated types for **routes, path params, query params, and the 46 real action bodies**. Type responses and entity CRUD bodies as `Record<string, unknown>` (or hand-written interfaces) — do *not* pretend the generated response types are real.
2. **Payload shapes must come from the Dolibarr PHP source** (next section). `../dolibarr-mcp/src/schemas.ts` and `formatters.ts` are a useful, battle-tested secondary source, but they were authored by inference and are not guaranteed complete.

## Deriving Real Payloads From the PHP Source

Clone `https://github.com/Dolibarr/dolibarr.git` and read `htdocs/**/class/api_<module>.class.php`. **Check out the tag matching the target instance** — `develop` is currently v24.0.0-beta and runs ahead of released instances.

Three things there answer what the spec cannot:

**1. Required create fields — `public static $FIELDS`.** Each API class declares its mandatory POST fields; `_validate()` throws `400 "<field> field missing"` for any that are absent. These are not in the spec at any level. Extracted from v24 source:

| Module | Required on create |
|---|---|
| `thirdparties` | `name` |
| `products` | `ref`, `label` |
| `invoices` / `supplier_invoices` / `proposals` / `supplier_proposals` / `supplier_orders` | `socid` |
| `orders` | `socid`, `date` |
| `contacts` | `lastname` |
| `projects` | `ref`, `title` |
| `tasks` | `ref`, `label`, `fk_project` |
| `tickets` | `subject`, `message` |
| `users` | `login` |
| `warehouses` / `memberstypes` | `label` |
| `categories` | `label`, `type` |
| `members` | `morphy`, `typeid` |
| `agendaevents` | `userownerid`, `type_code` |
| `contracts` | `socid`, `date_contrat` |
| `interventions` | `socid`, `fk_project`, `description` |
| `shipments` / `receptions` | `socid`, `origin_id`, `origin_type` |
| `stockmovements` | `product_id`, `warehouse_id`, `qty` |
| `bankaccounts` | `ref`, `label`, `type`, `currency_code`, `country_id` |
| `expensereports` | `fk_user_author`, `date_debut`, `date_fin` |
| `salaries` | `fk_user`, `label`, `amount` |
| `subscriptions` | `fk_adherent`, `dateh`, `datef`, `amount` |
| `donations` | `amount` |
| `objectlinks` | `fk_source`, `sourcetype`, `fk_target`, `targettype` |

Mark exactly these as `.requiredOption()` in Commander; everything else is optional.

**2. Create/update bodies are an open field bag.** `post()` does `foreach ($request_data as $field => $value) { $this->object->$field = ...; }` — it assigns *any* property of the underlying entity class. That is why the spec degenerates to `request_data: string[]`. Practical consequences:
- Model the common fields as explicit flags, but always provide a `--set <key=value>` / raw-JSON escape hatch so users can reach fields the CLI doesn't enumerate.
- `array_options` is the extrafields (custom fields) sub-object — worth a dedicated `--extrafield k=v` flag.
- `caller` is a reserved field used for trigger loop-prevention, not a data field.

**3. Response shape = entity public properties minus a blacklist.** `_cleanObjectDatas()` in `htdocs/api/class/api.class.php` strips internals before serialising, and encodes canonical field choices the CLI should mirror:

| Do not use | Use |
|---|---|
| `note` | `note_public` / `note_private` |
| `thirdparty` | `socid` / `thirdparty_id` |
| `contact` | `contact_id` |
| `project`, `fk_projet` | `fk_project` |
| `author` | `fk_user_author` |
| `mode_reglement` | `mode_reglement_id` |
| `cond_reglement` | `cond_reglement_id` |

It also drops `linkedObjects` (keeping only `linkedObjectsIds`), plus `pass`/`pass_indatabase` and various error/UI properties.

## Custom Modules Are Picked Up Automatically

Dolibarr is commonly extended with custom modules under `htdocs/custom/`, and those can ship
their own REST endpoints. **The CLI exposes them with no code changes** — this follows from
deriving the tree from the live spec, and has been verified end to end.

`dolGetModulesDirs()` scans every configured document root including the `custom` alt-root, so
`htdocs/api/index.php` registers a custom module's API class exactly like a core one, and it lands
in `/explorer/swagger.json` like everything else.

Demonstrated against live 23.0.3 with a throwaway module exposing three endpoints:

```
before:  Synced 30 modules, 428 operations.
after:   Synced 31 modules, 431 operations.

$ dolibarr widgetsapi --help
  get [options] <id>          Get properties of a widget
  list [options]              List widgets
  recalibrate [options] <id>  Recalibrate a widget
```

All three ran correctly, including `recalibrate` — a non-CRUD verb the naming rules had never
seen. Requirements for a custom module to appear:

- A descriptor at `custom/<module>/core/modules/mod<Module>.class.php`. Only the *filename* is
  matched to derive the module name; the file is never included or instantiated.
- An API class at `custom/<module>/class/api_<name>.class.php` declaring `<Name>Api` or `<Name>`.
- The module enabled (`MAIN_MODULE_<NAME>` in `llx_const`).
- A zero-argument constructor setting `$this->db` from the global — Restler instantiates API
  classes with no arguments, while `DolibarrApi::__construct` requires a database handle. Every
  core API class defines one for the same reason; omitting it yields a 500.

The module's spec tag comes from its API *class* name, so `WidgetsApi` produces a `widgetsapi`
command group. Custom modules control their own command name by naming the class deliberately.

## The API Surface Is Instance-Dependent

`htdocs/api/index.php` only registers an API class when its module is enabled:

```php
$enabled = true;
if (!isModEnabled($modulenameforenabled)) { $enabled = false; }
```

The v24 source ships **51** `api_*.class.php` classes, but the captured spec exposes only **38** tags — the difference (accountancy, holidays, productlots, emailtemplates, mailings, eventattendees, webhook, zapier, …) is modules that were disabled on that instance.

So "complete API coverage" is relative to a given instance's enabled modules. The CLI must:
- Treat a missing module as a normal outcome (404 on an entire path prefix), with a clear "module not enabled on this instance" hint rather than a generic 404.
- Consider building the command tree against the **union** of modules, and/or offering a `dolibarr modules` command that reports what the connected instance actually exposes.
- Never assume the committed spec matches the user's instance — this is what makes `check:spec` more than a nicety here.

Also from `htdocs/api/index.php`: alongside `DOLAPIKEY`, Dolibarr accepts a **`DOLAPIENTITY`** header selecting the entity in multi-company setups. Surface it as a global `--entity <id>` flag; without it the API falls back to the user's own entity and logs a performance warning.

## Dolibarr API Conventions

- **Base URL** ends in `index.php`: `http://<host>/api/index.php` (Dolibarr's `basePath` is `/api/index.php`)
- **Auth: `DOLAPIKEY` request header.** The spec declares `api_key` as a *query* parameter — ignore that; the header is what `../dolibarr-mcp` uses and what its contract tests verify (bad key → 401)
- **List params** (consistent across ~70 list endpoints): `limit`, `page` (0-indexed), `sortfield`, `sortorder` (`ASC`/`DESC`), `sqlfilters`, `properties`
- **`sqlfilters`** is Dolibarr's filter DSL, e.g. `(t.nom:like:'TheCompany%') and (t.datec:<:'20160101')`. Surface it as a raw `--sqlfilters` passthrough; it is the only way to do server-side filtering.
- **`properties`** restricts returned fields (comma-separated). Useful for narrowing wide table output.
- **Lists return a bare JSON array with no envelope and no total count.** There is no `totalElements`/`totalPages` — so `backbone/cli`'s `formatPage` (Spring Data `Page<T>`) does **not** apply. Build a `formatList`-style renderer that reports "showing N (page P)" and cannot report a grand total.
- **Errors** come back as `{ error: { message } }`. `../dolibarr-mcp/src/api-client.ts` has the status→hint mapping worth reusing (401 bad key, 403 permission, 404 missing id, 500 server, plus `ECONNREFUSED`/`ECONNABORTED` handling).

## Target Architecture

**Authoritative design: `docs/superpowers/specs/2026-07-22-dolibarr-cli-design.md`.** Read it
before making structural changes; this section is the summary.

The command tree is **derived from the connected instance**, not hand-written per module. Three
layers resolve at startup: static commands, generated commands from a cached manifest, and
(later) hand-crafted modules that claim `operationId`s and override the generated ones.

```
openapi/
  swagger.json          # committed reference capture: bundled bootstrap spec AND test fixture
src/
  index.ts              # program assembly: static → generated → crafted overrides
  registry.ts           # manifest → Commander commands
  manifest.ts           # Swagger 2.0 → slim manifest (pure, unit-tested)
  naming.ts             # operationId → command name (pure, unit-tested)
  commands/             # static: auth, context, config, sync, modules, api
  lib/
    client.ts           # generic request(); DOLAPIKEY + optional DOLAPIENTITY
    config.ts           # resolution order: flags → env → local file → context store
    errors.ts           # status hints + module-not-enabled detection
    output.ts           # formatList / formatDetail / formatSuccess; all honour --json
    pagination.ts       # limit/page/sortfield/sortorder helpers (NOT Spring Data)
  data/
    required-fields.json  # extracted from Dolibarr PHP source
    columns.json          # per-module table column hints
```

`sync` reads the instance's Swagger 2.0 **directly** — a command tree needs only paths, methods,
params and tags, so no OpenAPI 3 conversion is involved at runtime.

**Command names derive from `operationId`.** Two shapes: `<verb><Module>` (`listInvoices` →
`list`, `removeInvoices` → `delete`) and `<module><Rest>` (`invoicesCreateLine` → `create-line`).
Do not hand-name commands — extend `naming.ts` instead.

**`operationId` is NOT unique — do not key on it.** It is distinct across all 440 operations in
the reference capture, but a live Dolibarr 23.0.3 attaches `thirdpartiesCreateSocieteAccount` to
both `POST /thirdparties/{id}/accounts` and `POST /thirdparties/{id}/accounts/{site}`. Operation
identity is **`method + path`**; `operationId` is only an input to naming. Collision
disambiguation is therefore a required code path, exercised by the v23 fixture.

Patterns to carry over verbatim from `backbone/cli`:

- **Command factories**: static and crafted modules export `make<X>Command(): Command`, registered in `index.ts`. Generated commands are built by `registry.ts` instead — do not hand-write a file per module.
- **`runAction(command, fn)`** wraps every action for uniform error handling; the client resolves config per invocation.
- **`--json` everywhere**: every output helper checks `isJsonOutput(command)` and prints raw JSON instead of tables. JSON goes to stdout; warnings/errors/deprecations to stderr so piped JSON stays clean.
- **Contexts** (kubectl-style, in `lib/config.ts`): named `{ baseUrl, apiKey }` entries with an active one — valuable here since users commonly have several Dolibarr instances.
- **Config precedence**: CLI flags → env vars → local dotfile in cwd → active context in the `conf` store.

### Mapping the API to commands

Spec tags become the top-level command groups, **derived at `sync` time, not hardcoded**. The reference instance yields 38: `thirdparties`, `products`, `invoices`, `orders`, `proposals`, `contacts`, `projects`, `tasks`, `tickets`, `contracts`, `shipments`, `receptions`, `warehouses`, `stockmovements`, `bankaccounts`, `categories`, `users`, `members`, `subscriptions`, `agendaevents`, `documents`, `boms`, `mos`, `workstations`, `salaries`, `expensereports`, `donations`, `interventions`, `multicurrencies`, `knowledgemanagement`, `partnerships`, `recruitments`, `supplierinvoices`, `supplierorders`, `supplierproposals`, `setup`, `login`, `status`. Another instance will differ — treat this list as an example, never as a constant.

`../dolibarr-mcp` is useful for endpoint *semantics* (what an operation does, which params matter, how to display the result) and its `analysis/` folder has machine-readable inventories. But **derive the operation list from the spec, not from the MCP** — its tool list contains at least two duplicate registrations (`dolibarr_list_stock_movements`, `dolibarr_add_user_to_group`), which is part of why it counts 434 tools against 440 endpoints. The spec's `operationId`s are unique and complete; dedupe by those.

Note the size asymmetry: `products` (41), `setup` (41), `thirdparties` (39), `invoices` (29), `orders` (22) carry most of the surface; several modules have 5 or fewer.

Three things about this stack that are easy to get wrong, all learned the hard way:

- **Enable modules with `DOLI_ENABLE_MODULES`, never by inserting `MAIN_MODULE_*` rows.** The env
  var routes through `activateModule()`, which creates `/var/www/documents/api/temp`. Insert the
  const directly and the module looks enabled but the spec endpoint 500s with
  `Erreur temp dir api/temp not writable`.
- **Healthchecks must use `curl`, not PHP.** The image ships `allow_url_fopen=off`, so a
  `file_get_contents` probe fails forever while the container sits in `starting`.
- **`DOLI_ENABLE_MODULES` must have no spaces.** `docker-init.php` does `explode(',', …)` without
  trimming, so a YAML folded scalar turns `Banque` into `mod Banque` and activation fails.

Fetching the spec from a cold instance takes ~30–60 s — the explorer scans every module.

`../dolibarr-mcp/tests/` shows the unit + contract split worth copying, including skipping
cleanly when the instance is unreachable.

Do not copy the API key that sits in `../dolibarr-mcp/.mcp.json` into anything committed here.

## Adding a Command Group

1. Confirm the endpoints from `../dolibarr-mcp/analysis/endpoints-by-module.json` and the corresponding handlers in `../dolibarr-mcp/src/index.ts`.
2. **Open `htdocs/**/class/api_<module>.class.php` in the Dolibarr source** for that module: `$FIELDS` gives the required create options, the `post()`/`put()` bodies give the accepted fields, and the entity class gives the response fields. Cross-check against `../dolibarr-mcp/src/schemas.ts`, but let the PHP win on conflicts.
3. Create `src/commands/<module>.ts` exporting `make<Module>Command()`; register it in `src/index.ts`.
4. Pick table columns from what `../dolibarr-mcp/src/formatters.ts` chose to display for that entity — those are the fields the API actually returns.
5. `npm run typecheck` before considering it done.

## Workflow Triggers

### Ticket Planning

When a user message starts with `ticket:`, immediately load the `gitlab` skill and enter plan mode to document the feature, idea, or task before implementation.

### GitLab Issue Hygiene (ALWAYS — caveman rules)

ROCK SOLID RULE. NO EXCEPTION. WORK ON ISSUE = MOVE ISSUE.

1. **WORK START** → set issue label `status::in-progress` (scoped — auto-replaces any other `status::` label). Assign self.
2. **COMMIT** → message MUST end with `Refs: #<id>` (or `Closes: #<id>` if the commit finishes the work). Every commit. No exception.
3. **MR / PUSH FOR REVIEW** → set `status::needs-review`. Link MR to issue.
4. **MERGED TO `dev`** → keep `status::needs-review` and execute the manual smokes written into the MR's test plan / acceptance criteria yourself. Report PASS/FAIL per check with observed values.
5. **REACHED `main`** → close the issue. Remove `status::needs-review`.
6. **SPEC CHANGED / SCOPE DEAD** → close issue with a comment why. Do NOT leave stale open issues.

Caveman check before every commit: "issue linked? label moved?" If no → fix before commit.

If issue id unknown → ASK user, do not skip. If no issue exists for the work → create one first via `glab` (gitlab skill), then proceed.

### Epic Hygiene (ALWAYS — caveman rules)

BIG FEATURE = EPIC. FOLLOW-UP = ISSUE. NO EXCEPTION.

1. **WORK WILL BE 3+ ISSUES or SPANS REPOS** → create a group epic FIRST on `manfred-kunze-dev`. Epic description = problem + spec link + decision log. NO manual progress checklists — the child-issue list is the progress view.
2. **NEW SLICE ISSUE** → attach to epic at creation (`/epic &N`). Issue without epic on epic-scale work = bug in the process.
3. **MR FOLLOW-UP** → promote to issue BEFORE merge ("Create issue from thread" or `glab issue create`), attach to same epic, label `follow-up`. A follow-up that only lives in an MR is LOST WORK.
4. **MR DESCRIPTION** → reference the epic (`&N`) in addition to `Refs: #<id>`.
5. **STANDALONE ISSUE GROWS A FOLLOW-UP** → create epic, move both under it.
6. **MILESTONES ARE RELEASES** → never park a feature in a milestone.

Caveman check before merge: "follow-ups promoted? issue linked? epic linked?" If epic unknown → ASK user, do not skip.

Surfacing 440 endpoints is inherently epic-scale — expect one epic with per-module slice issues rather than a single mega-issue.
