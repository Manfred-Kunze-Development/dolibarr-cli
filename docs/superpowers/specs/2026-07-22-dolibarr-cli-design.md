# Dolibarr CLI — Design

**Date:** 2026-07-22
**Status:** Approved (design); implementation not started
**GitLab:** `manfred-kunze-dev/customers/manfred-kunze/dolibarr-cli`

## Goal

A CLI that surfaces the complete Dolibarr ERP/CRM REST API — every operation the connected
instance exposes, not a curated subset — with hand-crafted ergonomics added later for the
modules customers touch daily.

## Non-goals

- Reimplementing Dolibarr business logic. The CLI is a transport with good ergonomics.
- Offline operation. Every command except `config`/`context` requires a reachable instance.
- Supporting a fixed Dolibarr version. The command tree is derived per instance.

## Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Audience | Polished core + complete tail | Brief demands completeness; daily users need ergonomics. |
| Instance drift | Derive command tree from the live spec | Module set and version vary per customer; a pinned tree lies. |
| Core/tail assembly | Manifest registry with overrides | One registration path; real Commander commands so `--help` enumerates. |
| v1 scope | Engine only; craft later | All 440 endpoints reachable in one slice; craft based on real usage. |

## Why the spec cannot be trusted for payloads

Dolibarr publishes **Swagger 2.0** generated by Restler. Verified properties of the reference
instance's spec (440 operations, 38 modules):

- **Response schemas are placeholders.** 200 responses are declared `Obj` (107×), `string`,
  `string[]`, or `int64`. `listThirdparties` is typed `string[]` but returns thirdparty objects.
- **Entity CRUD request bodies are placeholders.** 101 of 148 definitions are
  `{ request_data: string[] }` — every `create*`/`update*` for the main entities.
- **46 action bodies are real** (`invoicesAddPaymentModel`, `bankaccountsTransferModel`,
  `createStockmovementsModel`, `tasksAddTimeSpentModel`, the `*ValidateModel`/`*CloseModel`
  family, …).

What *is* trustworthy: paths, methods, `operationId`, tags, and path/query parameters
(including genuinely useful descriptions). That is exactly enough to build a command tree,
and not enough to type payloads — which is why the tail is untyped by construction.

Payload ground truth is the Dolibarr PHP source (`htdocs/**/class/api_<module>.class.php`),
not the spec. See [Required create fields](#required-create-fields).

## Architecture

Three layers, resolved at startup:

1. **Static commands** — `auth`, `context`, `config`, `sync`, `modules`, `api`. Always present;
   work without a manifest.
2. **Generated commands** — one group per module, one command per operation, built from the
   cached manifest for the active context.
3. **Crafted commands** (future slices) — hand-written modules declare the `operationId`s they
   claim and replace the generated commands for those.

With no manifest, only static commands register and `--help` directs the user to run
`dolibarr sync`. A fresh install must never look broken.

```
src/
  index.ts              # program assembly: static → generated → crafted overrides
  registry.ts           # manifest → Commander commands
  manifest.ts           # swagger 2.0 → slim manifest (pure, unit-tested)
  naming.ts             # operationId → command name (pure, unit-tested)
  commands/             # static commands; later, crafted modules
  lib/
    client.ts           # request(), auth headers, timeouts
    config.ts           # flags → env → local file → context store
    errors.ts           # status mapping + module-not-enabled detection
    output.ts           # table / detail / json
  data/
    required-fields.json  # extracted from Dolibarr PHP source
```

## `sync` and the manifest

`dolibarr sync` fetches `{baseUrl}/explorer/swagger.json`, parses Swagger 2.0 **directly** — no
OpenAPI 3 conversion, since a command tree needs only paths, methods, params and tags — and
writes a slim manifest per context to `~/.config/dolibarr/manifests/<context>.json`.

```jsonc
{
  "dolibarrVersion": "21.0.2",
  "fetchedAt": "2026-07-22T09:15:00Z",
  "basePath": "/api/index.php",
  "modules": {
    "invoices": {
      "operations": [
        {
          "id": "listInvoices",
          "command": "list",
          "method": "get",
          "path": "/invoices",
          "summary": "List invoices",
          "pathParams": [],
          "query": [{ "name": "sqlfilters", "type": "string", "description": "…" }],
          "hasBody": false
        }
      ]
    }
  }
}
```

The spec endpoint accepts the same `DOLAPIKEY` auth as every other route
(`DolibarrApiAccess` is the global auth class), so `sync` needs no special credentials.

**Two verified failure modes, each with a dedicated message:**

| Cause | Behaviour |
|---|---|
| `API_EXPLORER_DISABLED` set | Explorer routes refuse. Fall back to the bundled spec; suggest `dolibarr sync --spec <file>`. |
| `api/temp` missing or not writable | Server returns a literal `500 temp dir api/temp not writable`. Detect and explain — it is a server-side setup problem, not a CLI bug. |

The second is not exotic: it is what a Dolibarr instance does whenever the API module was
enabled by writing `MAIN_MODULE_API` straight into `llx_const` instead of going through
`activateModule()`, because the directory is created as an activation side effect.
Reproduced locally, then fixed in our own compose stack — see [Local instances](#local-instances).

`sync` is slow against a cold instance (the explorer scans every module: ~30–60 s, ~0.9 MB for
30 modules), so it must show a spinner and must not be on the hot path of ordinary commands.

A bundled spec ships as the default manifest source so the CLI is usable before the first
`sync`, and `--spec <file>` accepts a hand-supplied spec. The bundled spec and the unit-test
fixture are the same committed artifact (`openapi/swagger.json`, the 440-operation reference
capture) — one file, so a drift in it fails tests rather than silently changing behaviour.

`dolibarr modules` prints what the active context's manifest contains — module name, operation
count, and the instance's Dolibarr version — with `--refresh` as an alias for re-running `sync`.

## Command-name derivation

Dolibarr `operationId`s take two shapes.

**`operationId` is not a reliable primary key.** It holds on the reference capture (440/440
distinct) but fails on a live Dolibarr 23.0.3, where `thirdpartiesCreateSocieteAccount` is
attached to two different paths:

```
POST /thirdparties/{id}/accounts
POST /thirdparties/{id}/accounts/{site}
```

The identity of an operation is therefore **`method + path`**, and that is what crafted modules
claim and what the manifest keys on. `operationId` is used only as the input to name derivation.

**Shape A — root CRUD:** `<verb><Module>` → canonical verb.

| operationId | Command |
|---|---|
| `listThirdparties` | `list` |
| `retrieveThirdparties` | `get` |
| `createThirdparties` | `create` |
| `updateThirdparties` | `update` |
| `removeThirdparties` | `delete` |

**Shape B — sub-resource/action:** `<module><Rest>` → strip module prefix, kebab-case the
remainder, normalise the leading verb token (`retrieve`/`get` → `get`; `remove`/`del`/`delete`
→ `delete`).

| operationId | Command |
|---|---|
| `thirdpartiesRetrieveByEmail` | `get-by-email` |
| `invoicesCreateLine` | `create-line` |
| `invoicesRemoveLine` | `delete-line` |
| `productsDelSubproducts` | `delete-subproducts` |
| `thirdpartiesMerge` | `merge` |

The `Del`/`Remove` inconsistency is Dolibarr's, absorbed by the normalisation table.

**Collision handling is mandatory, not a safety net.** When two operations derive the same
command name, disambiguate by appending the extra path parameters of the longer path
(`create-societe-account` and `create-societe-account-by-site`), and if that still collides, fall
back to the full kebab-cased path. Ordering must be deterministic — sort by path before
assigning — so the same spec always yields the same command names.

**Verified against two real specs:**

| Spec | Modules | Operations | Distinct operationIds | Collisions after derivation |
|---|---|---|---|---|
| Reference capture | 38 | 440 | 440 | 0 |
| Live Dolibarr 23.0.3 | 30 | 428 | 427 | 1 (handled as above) |

Both are committed as test fixtures so derivation is a regression test against two genuinely
different surfaces rather than one.

Known cosmetic wart, accepted: redundant nouns survive, e.g.
`dolibarr invoices create-invoice-from-order`. Stripping a module-noun token after the verb is
possible but fragile; revisit only if it annoys real users.

## Generic command shape

- **Path params** → positional arguments, in path order.
- **Query params** → flags, generated from the spec with its descriptions as help text.
- **Bodies** → `--data @file.json`, `--data '<json>'`, repeatable `--set key=value`
  (dot-paths for nesting), and `--extrafield k=v` mapping into `array_options`.

When both are supplied, `--data` provides the base object and `--set`/`--extrafield` are applied
on top, so a file can be used as a template and overridden per invocation. Supplying `--data`
twice is an error rather than a silent merge.

Bodies need this treatment because Dolibarr's `post()` does
`foreach ($request_data as $field => $value) { $this->object->$field = …; }` — it assigns any
property of the underlying entity. The body genuinely is an open field bag, so the CLI must
never pretend to know the full field list.

Reserved: `caller` is a trigger-loop-prevention field, not user data.

### Required create fields

Each API class declares `public static $FIELDS`; `_validate()` throws
`400 "<field> field missing"` for omissions. These appear nowhere in the spec. Extracted from
source and shipped as `src/data/required-fields.json`, they become `.requiredOption()` so users
get a local error instead of a server 400.

| Module | Required |
|---|---|
| `thirdparties` | `name` |
| `products` | `ref`, `label` |
| `invoices`, `supplier_invoices`, `proposals`, `supplier_proposals`, `supplier_orders` | `socid` |
| `orders` | `socid`, `date` |
| `contacts` | `lastname` |
| `projects` | `ref`, `title` |
| `tasks` | `ref`, `label`, `fk_project` |
| `tickets` | `subject`, `message` |
| `users` | `login` |
| `warehouses`, `memberstypes` | `label` |
| `categories` | `label`, `type` |
| `members` | `morphy`, `typeid` |
| `agendaevents` | `userownerid`, `type_code` |
| `contracts` | `socid`, `date_contrat` |
| `interventions` | `socid`, `fk_project`, `description` |
| `shipments`, `receptions` | `socid`, `origin_id`, `origin_type` |
| `stockmovements` | `product_id`, `warehouse_id`, `qty` |
| `bankaccounts` | `ref`, `label`, `type`, `currency_code`, `country_id` |
| `expensereports` | `fk_user_author`, `date_debut`, `date_fin` |
| `salaries` | `fk_user`, `label`, `amount` |
| `subscriptions` | `fk_adherent`, `dateh`, `datef`, `amount` |
| `donations` | `amount` |
| `objectlinks` | `fk_source`, `sourcetype`, `fk_target`, `targettype` |

**This table is version-sensitive.** It was extracted from v24.0.0-beta (`develop`). It must be
re-extracted per supported Dolibarr major, and the extraction script lives in the repo so that
is a one-command job. When the table and the instance disagree, the server's 400 remains the
backstop — client-side checking is an ergonomic improvement, never the source of truth.

## Client

A single `request()` function. No `openapi-fetch` in v1: with an engine-only scope every command
goes through the generic path, so a typed client would have zero call sites. It arrives with the
first crafted module, together with the `swagger2openapi -p → openapi-typescript` build step
(`-p` is required; without it conversion aborts on a malformed path parameter in
`POST /proposals/{id}/contact/{contactid}/{type}/{source}`).

- Auth: `DOLAPIKEY` header. The spec advertises an `api_key` *query* parameter; the header is
  what the server prefers and what avoids leaking keys into logs.
- `DOLAPIENTITY` header via a global `--entity <id>` for multi-company setups. Without it the
  API falls back to the user's own entity and logs a performance warning.
- Config precedence: CLI flags → env vars → local dotfile → active context.

## Errors

Status mapping adapted from `../dolibarr-mcp/src/api-client.ts` (401 bad key, 403 permission,
404 missing, 500 server, plus `ECONNREFUSED`/`ECONNABORTED`). Dolibarr returns
`{ error: { message } }`.

The manifest enables one mapping the MCP could not do: a **404 against a module absent from the
manifest** reports *"module not enabled on this instance"* with the list of enabled modules,
rather than "check that the ID is correct".

This matters because the API surface is instance-dependent — `htdocs/api/index.php` registers an
API class only when `isModEnabled()` passes. The v24 source ships 51 API classes; the reference
instance exposes 38.

## Output

- Arrays → table. Columns come from `src/data/columns.json` (a per-module hint list, seeded from
  the fields `../dolibarr-mcp/src/formatters.ts` chose to display), falling back to the first six
  scalar keys of the first row when a module has no entry. `--properties` passes through to the
  API so narrowing happens server-side; `--columns a,b,c` overrides locally.
- Objects → key/value detail.
- `--json` → raw JSON on stdout. Warnings and errors always go to stderr so piped JSON stays clean.

Dolibarr list endpoints return a bare array with **no envelope and no total count**. The footer
reads `N results (page P)`. The CLI never fabricates a total, and there is no Spring-style
`Page<T>` handling to port from `backbone/cli`.

## Local instances

`compose.yml` provides three Dolibarr versions — previous, current, next — which is both the
local dev story and the CI matrix. Versions are selected by Docker profile so a developer runs
one while CI can run all three.

| Profile | Image | Version | URL |
|---|---|---|---|
| `previous` | `dolibarr/dolibarr:22` | 22.0.5 | `http://localhost:8022` |
| `current` | `dolibarr/dolibarr:23` | 23.0.3 | `http://localhost:8023` |
| `next` | `dolibarr/dolibarr:develop` | 24.0.0-beta | `http://localhost:8024` |

Each instance comes up fully usable with no UI interaction:

- Modules are activated via the image's `DOLI_ENABLE_MODULES`, which routes through
  `activateModule()` and runs the activation side effects. **Enabling modules by inserting
  `MAIN_MODULE_*` rows directly does not work** — the module appears enabled but
  `/var/www/documents/api/temp` is never created and the spec endpoint 500s.
- A fixed admin API key is seeded by SQL through the image's `docker-init.d` hook, which runs
  after both module activation and SuperAdmin creation.
- The healthcheck probes `/api/index.php/status` with that key, so "healthy" means the API is
  genuinely reachable and authenticating. It uses `curl`, not PHP: the image ships
  `allow_url_fopen=off`, so a `file_get_contents` probe silently never succeeds.

### Instance-dependence, measured

The two specs we have differ substantially, which is the empirical basis for deriving the
command tree rather than hardcoding it:

| | Reference capture | Live 23.0.3 (16 modules enabled) |
|---|---|---|
| Modules | 38 | 30 |
| Operations | 440 | 428 |
| Paths | 285 | 287 |

Present in the live instance but not the reference: `emailtemplates`, `memberstypes`,
`objectlinks`, `paiements`, `productlots`. Present in the reference but not live: `boms`, `mos`,
`workstations`, `knowledgemanagement`, `partnerships`, `recruitments`, `salaries`,
`expensereports`, `donations`, `interventions`, `multicurrencies`, `supplierproposals`,
`receptions`.

Note the path count moves in the *opposite* direction to the operation count — fewer operations
across more paths. Any assumption that one instance's surface is a superset or subset of
another's is wrong.

## Testing

TDD throughout.

- **Unit** (no network): manifest builder, name derivation including collision disambiguation,
  param/body assembly, error mapping, output formatting. Run against **both** committed spec
  fixtures (reference 38-module and live 23.0.3 30-module) — the second is what catches the
  duplicate-`operationId` case the first misses.
- **Contract** (live): against this repo's `compose.yml`, skipping cleanly when the instance is
  unreachable so a developer without Docker running still gets a green unit suite.
- **CI matrix**: previous / current / next profiles, so version-sensitive behaviour
  (`required-fields.json`, module availability, spec quirks) is caught before a customer does.

## Delivery

- npm package; bins `dolibarr` and `doli`.
- `.gitlab-ci.yml` mirroring `backbone/cli`'s build-and-publish.
- Epic-scale work: one epic on `manfred-kunze-dev`, then tracer-bullet slices —
  config/context → client → manifest+sync → registry → generic commands → `api` passthrough →
  modules/error mapping → packaging.

## Deferred

- `openapi-fetch` + generated types (arrives with the first crafted module).
- Crafted modules, prioritised by observed usage.
- Caching of dictionary/`setup` lookups.

## Risks

| Risk | Mitigation |
|---|---|
| Tail is untyped | Unavoidable — the spec has no payload types. Contract tests carry the weight. |
| `required-fields.json` drifts from instance version | Re-extraction script in repo; server 400 is the backstop. |
| Explorer disabled on hardened instances | Bundled spec + `--spec <file>`. |
| Manifest parse cost at startup | Keep the manifest slim; measure before optimising. |
| Bundled spec ages | `sync` is the intended path; the bundle is only a bootstrap. |
